#### Phase 2: Disable Self-Healing locally and push to github

3. **Edit the ArgoCD Application manifest:** On your local machine or repository workspace,
     set `selfHeal: false` in `infrastructure/05-aws-k8s/k8s-manifests/observability/ritual-roast-app.yml`:

```yaml
syncPolicy:
  automated:
    prune: true
    selfHeal: false

```

**********************************************************************************************************

4. **Sync Git repository:** Commit and push this change so your repository stays in sync with what is running on the cluster:

```bash
git add infrastructure/05-aws-k8s/k8s-manifests/observability/ritual-roast-app.yml
git commit -m "ops: disable selfHeal for canary deployment"
git push origin main

```

**********************************************************************************************************

5. **Apply the policy change directly to the cluster:**

Instead of waiting 3 minutes for ArgoCD to pick up the change, we can apply the change immediately with the following:

```bash
# Refresh the root ArgoCD application
kubectl annotate application root-observability -n argocd argocd.argoproj.io/refresh=normal --overwrite
```

annotating root-observability refreshes the parent App-of-Apps (causing it to re-render and apply child Application CRDs).
After a few seconds we can verify that the change occured:

```bash
k get application ritual-roast-workloads -n argocd -o yaml | grep -A 3 -B 3 "selfHeal:"
```

The output should look like:

```bash
[root@ip-10-16-117-217 bin]# k get application ritual-roast-workloads -n argocd -o yaml | grep -A 3 -B 3 "selfHeal:"
  syncPolicy:
    automated:
      prune: true
      selfHeal: false
    syncOptions:
    - CreateNamespace=true
status:
[root@ip-10-16-117-217 bin]# 
```

#### Phase 3: Execute Canary Traffic Splitting

To avoid cloning the entire repository onto the control plane node, we stream individual canary manifests directly. Private GitHub repositories return 404 errors for unauthenticated raw URLs, so we pass the GITHUB_PAT authorization header via curl. We include the --fail flag to catch HTTP errors before piping into kubectl apply -f -, safely applying updates in-memory.

6. Export the GitHub PAT: inside the aws ssm session execute the following command:
```bash
export GITHUB_PAT="PASTE GitHub PAT"
```

7. **THIS IS IMPORTANT:** Before executing the canary, it is ideal to inject traffic through the system to facilitate the kiali visualization.
   So open `05-aws-k8s/documents/Traffic_injection_methods_for_Observability.txt` and follow the instructions.


8. **Apply 10% Canary Variants:**
```bash
# 10% Frontend Canary
curl --fail -H "Authorization: token ${GITHUB_PAT}" \
  -sSL "https://raw.githubusercontent.com/ManunEbo/Terraform-AWS-Ritual-Roast-Part-2-Containerised/main/infrastructure/05-aws-k8s/k8s-manifests/canary-variants/vs-frontend-canary-10.yml" \
  | k apply -f -
```

```bash
# 10% Backend Canary
curl --fail -H "Authorization: token ${GITHUB_PAT}" \
  -sSL "https://raw.githubusercontent.com/ManunEbo/Terraform-AWS-Ritual-Roast-Part-2-Containerised/main/infrastructure/05-aws-k8s/k8s-manifests/canary-variants/vs-backend-canary-10.yml" \
  | k apply -f -
```

Now watch the traffic on kiali.

Using the same technique, we can progress through the canaries: 30, 50, 70, 90, 100, bluegreen and shadow

**********************************************************************************************************

9. **Verify traffic & metrics:** Send requests through the LoadBalancer DNS and monitor
     logs/Grafana dashboards to ensure `v2` handles ~10% of traffic without errors.
     
     Note, you must do each of these in a new shell to avoid log monitoring limits.

Monitor logs with:

a. Stream Real-Time Logs for All v2 Pods

```bash
k logs -n dev -l version=v2 --all-containers=true -f --tail=30
```

b. Stream Specific Service Logs (Frontend vs. Backend). Open separate terminal tabs or
   SSM sessions to monitor the frontend and backend independently:

```bash
# Stream Backend v2 logs (Go app)
k logs -n dev -l app=backend,version=v2 -f --tail=50

# Stream Frontend v2 logs (Vite app)
k logs -n dev -l app=frontend,version=v2 -f --tail=50
```

c. Filter live logs for errors: Filter out normal HTTP 200 traffic to focus strictly
   on failures (5xx HTTP status codes or unhandled exceptions):

```bash
kubectl logs -n dev -l version=v2 -f --tail=100 | grep -E -i "error|exception|fail|5[0-9]{2}"
```

**********************************************************************************************************

10. **Progress through remaining stages:** Repeat step 8 for `30%`, `50%`, `70%`, `90%`, and finally `100%`
   (`vs-frontend-canary-100.yml` and `vs-backend-canary-100.yml`).

**********************************************************************************************************

#### Phase 4: Lock In Git as Source of Truth & Re-Enable Self-Healing

> **Critical:** Do **not** re-enable `selfHeal: true` until you have updated Git.
    If you enable `selfHeal` while Git still points to the `v1` routing manifest,
    ArgoCD will instantly wipe out your live `v2` rollout and revert traffic back to `v1`.

11. **Update Git to match the 100% `v2` state:** In your local repository, open
    `infrastructure/05-aws-k8s/k8s-manifests/dev-apps/routing/istio-routing.yml` and change ONLY the weight values:
    - `frontend-route`, the last http rule (the weighted rule with no `match:`): v1 `weight: 0`, v2 `weight: 100`
    - `backend-route`, the weighted rule: v1 `weight: 0`, v2 `weight: 100`

    Do NOT replace the file with the `canary-100` variant files. `istio-routing.yml` holds other resources as well,
    and ArgoCD runs with `prune: true`, so anything missing from the file would be deleted from the cluster.
    Do NOT touch the `/kiali` rule or the two cookie rules.

12. **Commit the new baseline:**

```bash
git add infrastructure/05-aws-k8s/k8s-manifests/dev-apps/routing/istio-routing.yml
git commit -m "feat(routing): promote v2 to 100% stable production release"
git push origin main

```


13. **Re-enable `selfHeal: true` in the application manifest:** Edit `infrastructure/05-aws-k8s/k8s-manifests/observability/ritual-roast-app.yml`:
```yaml
syncPolicy:
  automated:
    prune: true
    selfHeal: true

```


14. **Commit, push, then refresh ArgoCD:** On your local machine:
```bash
git add infrastructure/05-aws-k8s/k8s-manifests/observability/ritual-roast-app.yml
git commit -m "ops: re-enable selfHeal enforcement"
git push origin main

```

Then, in the SSM session on the control plane, refresh the root application as in step 5 so the change applies immediately:
```bash
kubectl annotate application root-observability -n argocd argocd.argoproj.io/refresh=normal --overwrite
```

15. **Final Verification:** Check ArgoCD to ensure the application status transitions back to **Synced** and **Healthy**.

```bash
k get application -n argocd
```

Alternatively:

To inspect the detailed status and live sync conditions of the specific workloads application `ritual-roast-workloads` use:

```bash
kubectl get application ritual-roast-workloads -n argocd -o jsonpath='Sync: {.status.sync.status} | Health: {.status.health.status}{"\n"}'
```
